# Vercel deployment

The root `app.py` exports the FastAPI backend and registers the built React frontend. `pyproject.toml` selects Python 3.12 and runtime dependencies. Vercel's FastAPI adapter promotes the static frontend to the CDN. `vercel.json` builds the frontend, then runs release-time PostgreSQL migration/seeding. No localhost backend URL is used in production: frontend requests remain same-origin.

Required production environment:

- `DATABASE_URL`: supplied by the Vercel Neon integration; the app normalizes `postgresql://` to the psycopg SQLAlchemy dialect.
- `JWT_SECRET`: random stable signing secret, stored as a Vercel Secret.
- `AUTO_SEED=false`: cloud startup does not generate data. The release command initializes an empty database once; subsequent releases preserve it.

Secrets are not included in source uploads. `.env.production.local` contains redacted placeholders when Vercel refuses to export sensitive values, and is ignored. Database initialization runs inside Vercel using injected credentials; it does not require revealing the connection string locally.

## Redeploy

From the linked repository, run `vercel deploy --prod --scope resum-projects` with Vercel CLI installed and authenticated. On the development host, the workspace-local equivalent is:

```powershell
node .tools/vercel/node_modules/vercel/dist/vc.js deploy --prod --yes --scope resum-projects
```

The build runs `npm run build && python scripts/initialize_cloud.py`. Migration and seeding acquire the same PostgreSQL advisory transaction lock as allocation workflows. If a workflow is active during release, retry after it completes. Data is not reset by deployments.

## Serverless behavior

Cloud cold starts do not migrate, reseed or mark other instances' running workflows failed. PostgreSQL advisory locks serialize optimization across instances. Inventory approval continues to use database transactions, row locks and version checks. Polling refreshes persisted API data when event/WebSocket delivery is unavailable or attached to another instance. Transient event logs remain process-local; durable run/execution/message/audit records remain in PostgreSQL.

Maximum request duration is configured to 300 seconds. Long forecasting batches, especially full-network random forests, should be moved to a durable job system if they approach function limits. The initial release seeds 584,000 history rows and can take several minutes. The app uses the existing synthetic demo accounts; all dataset contents are generated demonstration data.
